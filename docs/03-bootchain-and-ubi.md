# 3. Новая цепочка и единый UBI

Основой была EU UBI-ветка PR #21640 на `d4ebffe538ab94d9b5a604f4bba28325f38ed3d8`, с локальными изменениями. Другие регионы и ревизии не проверялись. План установки через UART из PR не выдаётся за выполненную здесь последовательность.

## Что готовили до записи

- BL2/TF-A и U-Boot для MT7986, SPI NAND UBI и DDR3-профиля. Соответствие Kconfig/map проверили программно; это ещё не испытание DDR training.
- Redundant env: действующий `CONFIG_ENV_REDUNDANT=y` вместо устаревшего `CONFIG_SYS_REDUNDAND_ENVIRONMENT`. Итоговый конфиг выбирал два UBI env volumes, размер каждого `0x1f000`.
- Hardened env: `&&`/`if` вместо продолжения после отказа, `mw.b` для заполнения байтами, checks размеров и SHA256 перед BL2/FIP. Эти изменения не делают запись атомарной и не заменяют readback.
- Factory-кандидат из EEPROM и базового MAC именно этого роутера: 1 МиБ с заполнением `0xff`, EEPROM с offset 0, MAC с offset `0x8000`. Сохранили все 20 480 байт EEPROM, а не только 4096 байт DTS-cell.
- Две заранее заполненные env-копии, CRC и roundtrip с `mkenvimage`. Flags 1/0 выбирали первую копию; первый bootcmd шёл в recovery, затем TFTP. Удалили зависимость от `_firstboot` и автоматических двух saveenv.
- Образ UBI с `fip` static, `ubootenv`, `ubootenv2`, `fit`, `recovery`, `rootfs_data` dynamic; последний с autoresize.

Геометрия для этого случая: NAND page 2048, PEB 131 072, LEB 126 976 байт; data offset 4096. Это наблюдения конкретного чипа. Generic UBI layout нельзя применять без проверки геометрии.

## Три исторические фазы

| Имя в migration map | Offset | Размер | Назначение |
| --- | ---: | ---: | --- |
| bl2 | 0 | 1 048 576 | Ранняя ступень загрузки |
| factory | 1 048 576 | 1 048 576 | Данные этого устройства |
| ubi | 2 097 152 | 132 120 576 | Остальная NAND под UBI |

Исполнитель перед каждой фазой заново проверял RAM root/tmpfs, отсутствие неожиданных mounts, фактические offsets/flags, хеш writer и payload, RAM reserve, ECC и предыдущую фазу. Уже существующий журнал попытки блокировал повторный запуск.

Исторические команды ниже обобщают только приватный RAM-путь и цели, вычисленные по карте. **Они уничтожают данные; это запись прошлого действия, не инструкция для исполнения.**

```sh
mtd write <RAM_DIR>/factory.bin <FACTORY_MTD_FROM_MAP>
ubiformat <UBI_MTD_FROM_MAP> -s 2048 -O 2048 -f <RAM_DIR>/ubi.ubi -y
ubiattach /dev/ubi_ctrl -m <UBI_NUMBER_FROM_MAP> -d 0
mtd erase <BL2_MTD_FROM_MAP>
mtd write <RAM_DIR>/bl2.bin <BL2_MTD_FROM_MAP>
```

`mtd write` в первой строке переносил собственный подготовленный factory. `ubiformat` заменял старую UBI-схему целым заранее проверенным образом. `ubiattach` подключал результат для логического чтения томов. Последние две команды стирали весь BL2-раздел и записывали padded BL2. Фактические MTD-номера той карты и exit codes видны в [выдержках логов](../evidence/README.md), но переносить их на другой запуск нельзя.

После factory сравнили полный readback; после UBI — все шесть имён/типов и пять payload hashes, отсутствие update/corruption; перед BL2 повторили это ещё раз. BL2 payload дополнили до 262 144 байт; проверили весь раздел включая `0xff`-хвост. Счётчики ошибок не выросли. Журналы всех трёх фаз имеют PASS и `reboot=false`.

После attach rootfs_data вырос с 1 до 318 LEB. В UBI было 1008 good PEB, 0 bad/corrupted и резерв 20 PEB. Ноль свободных LEB после autoresize означает распределённую ёмкость, а не заполненный overlay.

На этом checkpoint новая NAND была записана, но роутер ещё работал в прежней RAM-системе. Это **не boot test**. Старые vendor boot/env/слоты уже перекрыты. Только отдельно согласованный следующий ребут показал, запускается ли новая цепочка. До него потеря питания могла лишить текущего доступа; гарантированного UART-восстановления не было.
