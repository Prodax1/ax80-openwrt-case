# 2. Стоковый доступ и две RAM-среды

Стартовая версия OEM — 1.1.2. Временный root-доступ получили через telnet-enable: офлайн изменили один DDNS service в зашифрованном конфигурационном архиве, сохранили остальные entries и проверили encode/decode roundtrip. Архив владелец импортировал в штатный интерфейс. Это не смена постоянного SSH-загрузчика. Применимость к другой версии OEM не доказана.

Скрипт подготовки использовал формат из публичного CVE-2022-30075 и адаптацию интерфейса AX80; его текст в репозитории обезличен, ключевые константы и строка учётных данных исключены. Сам исходный конфиг и результат с настройками устройства не публикуются.

## Диагностическая ветка

В первой RAM-системе резерв старого `kernel` вырос с 83 до 115 LEB по 126 976 байт. Вот действительно выполненная команда этого этапа:

```sh
ubirsvol /dev/ubi0 -n 1 -S 115
```

Она изменяет таблицу UBI, сохраняя данные kernel. После операции ёмкость стала 14 602 240 байт, свободных LEB осталось 53, прежний hash kernel сохранился. Номер тома относится только к той проверенной старой карте. Это запись NAND, даже без замены payload.

Затем в том записали read-only диагностический FIT:

```sh
ubiupdatevol /dev/ubi0_1 <RAM_DIR>/ax80-eu-luci-readonly-diagnostic.itb
```

Путь обезличен. Команда заменяет содержимое тома, а не разметку всего чипа. После чтения назад данные занимали 9 288 608 байт; `corrupted` и `upd_marker` были нулевыми. Соседние payload проверили отдельно. Далее отдельный ребут действительно загрузил diagnostic RAM root, восемь read-only MTD и отсутствие UBI autoattach/Wi-Fi. Именно здесь получили 128 МиБ backup без OOB.

## Почему этот путь пришлось оставить

Read-only карта защищала NAND, но из неё нельзя было записать подготовленную migration-систему. Проверенного kexec не было. Обычная перезагрузка не выбирала другой образ. Ошибка подготовки — не проверить выход из диагностической среды до входа в неё.

Пока старая цепочка ещё существовала, воспользовались vendor recovery, вернулись в OEM и повторили telnet-доступ. Потом через официальный initramfs перешли к специально подготовленному writable migration FIT. В этом втором проходе резерв kernel рос уже с 27 до 115 LEB; это другое исходное состояние, его нельзя склеивать с первым resize.

Историческая вторая доставка включала:

```sh
<RAM_DIR>/busybox ubirsvol -n 1 -s 14602240 /dev/ubi0
<RAM_DIR>/busybox ubiupdatevol /dev/ubi0_1 <RAM_DIR>/initramfs.bin
ubiupdatevol /dev/ubi0_1 <RAM_DIR>/migration.itb
```

Первая команда задаёт размер в байтах, вторая пишет официальный RAM-образ, третья — manual migration FIT после его загрузки и повторной сверки карты. Между этапами проверяли payload, neighbours и новый running identity. Старые BL2/FIP/factory/env ещё не заменяли. Архивы [stock-to-reference](../scripts/history/execute_stock_to_reference.py.txt) и [reference-to-migration](../scripts/history/execute_reference_to_migration.py.txt) сохраняют проверки и порядок.

Migration FIT был 9 323 820 байт. После запуска подтвердили RAM root, отсутствие autoattach, три ожидаемых раздела и `MTD_WRITEABLE` (`0x400`). Initramfs сам по себе этого не гарантирует: решают ядро и DTS. Старая нумерация MTD уже изменилась, поэтому запись дальше выбирала цель по имени, offset и size.
